# API v1 implementation plan

Status: **planned contracts and requirements; implementation varies and requires verification**. The repository contains an API, migrations and tests, but route presence does not prove complete behavior; consult the [Phase 1 assessment](phase1-assessment-and-reconciliation-plan.md) and its resulting evidence. The [Phase 1 Scrum roadmap](api-demo-scrum-roadmap.md) defines the fictional-data demo, including mixed needs and split referrals. The [database design](database-design.md) describes the proposed Phase 1 mapping and links to the earlier full-product proposal. Late-dispute behavior remains a proposed later increment subject to validation.

## Platform and delivery

Use .NET 10 minimal APIs with feature route groups, thin handlers, separate request/response DTOs, EF Core and the Npgsql provider. Plan OpenAPI for `/api/v1`, liveness and a separate PostgreSQL readiness check. Keep one deployable API and the planned Expo React Native Web client. Existing endpoints and dependencies require assessment; no endpoint or check in this plan is claimed complete solely because it is listed.

For local development, install the .NET 10 SDK, Docker and a matching `dotnet-ef` tool; start a password-protected isolated PostgreSQL container with a persistent volume and supply `ConnectionStrings__HelpingHands` as an environment variable, locally using the ignored root `.env` and launcher described in the [README](../README.md). Production secrets belong in the deployment environment or a secret manager. Use the actual API/data project and startup project after verifying the current project layout and EF tooling; generate named migrations with `dotnet ef migrations add` and apply them locally with `dotnet ef database update`. Review generated migration and SQL before applying; commit migration and snapshot with the model change. Use a fresh database for initial-migration testing and an existing previous-version database for upgrade testing. Shared deployments run reviewed migration SQL as a controlled step after backup, with a tested restore and forward-fix plan; do not auto-migrate on app startup. Never commit credentials.

## IDs and references

Each table, including role, join and history tables, has a UUID primary key generated by the server; foreign keys use UUID. Join tables retain unique constraints on their original key pairs; subtype tables retain the recipient UUID as both PK and FK. UUIDs are the stable route and relationship identifiers, never authorization credentials.

Persist a separate immutable reference for beneficiary (`BEN`), recipient application/profile (`REC`), request (`REQ`), referral (`REF`) and outcome (`OUT`). The application and its resulting recipient profile share the same recipient record and reference. Format is `PREFIX-` followed by a zero-padded decimal sequence of at least eight digits, for example `REQ-00000001`; numbers may grow beyond eight digits up to the PostgreSQL sequence limit and are never recycled. Maintain one PostgreSQL sequence per prefix, allocate with `nextval` on the server at creation, and enforce a unique reference index on each table. Sequence gaps after rollback or failed requests are expected; they convey no counts, ordering guarantees across transaction commits, or secrecy. Do not accept client-supplied references or derive them by truncating UUIDs. Return `id` and `reference` in resource DTOs. Support exact `reference` filtering on authorized list endpoints; enforce the same involvement checks as UUID lookup and do not disclose whether an inaccessible reference exists. Future user-facing records needing references require a reviewed migration and prefix.

## API contracts and authorization

Routes below are planned under `/api/v1`; `{id}` is a UUID. Use JSON DTOs, UTC timestamps and decimal quantities; uploads use multipart form data. Return `201` with `Location` for creation, `204` for successful commands without a response, and stable RFC 9457 Problem Details for errors: `400` invalid input, `401` unauthenticated, `403` denied where disclosure is safe, `404` missing or concealed resource, and `409` invalid transition, stale version or allocation conflict. Lists use bounded page size (default 25, maximum 100), stable ordering and opaque cursor; search and pagination apply after authorization. Include a concurrency version in mutable resource responses and require it for updates, returning `409` when stale. Define DTO fields and detailed transitions against the SRS before coding each feature.

Beneficiary signup accepts `displayName`, `email`, `password`, optional `contactDetails`, and `isFamily`; it uses the same display name for the account and linked profile. Charity signup accepts `representativeDisplayName`, `email`, `password`, `organizationName`, `contactDetails`, and optional `registrationInformation`. Return the account UUID and the created business-record UUID/reference, without credentials or an authentication cookie. Signup and related profile/application/membership writes commit atomically; invalid input, duplicate email or a failed related write must not leave partial records. These request/response shapes are implemented on `main`; PostgreSQL integration tests and the post-merge workflow passed for PR #82.

Charity application detail returns registration information, attachment metadata (`id`, `originalName`, `mediaType`, `sizeBytes`, `uploadedAt`) and decision history (`decision`, `reason`, `actorUserId`, `decidedAt`) to coordinators, administrators and active representatives. Attachment content remains available through the authorized attachment route; storage keys are never returned. Approval requires registration information or an uploaded document; rejection requires a reason. Decisions apply only to pending applications, use the supplied concurrency version, and atomically record the decision and state change. Pending, rejected and inactive charities are ineligible for new referrals. Signup may precede submission of a supporting document.

Administrator and Coordinator remain distinct roles, but Administrator inherits all Coordinator permissions. Authorization still checks the user's record involvement where an action or record is limited to an owner, representative membership or assignment.

Versioned business endpoints require authentication except `GET /api/v1/auth/antiforgery`, `POST /api/v1/auth/register/beneficiary`, `POST /api/v1/auth/register/charity`, and `POST /api/v1/auth/login`; `/health`, `/ready`, and the development-only OpenAPI endpoint are operational endpoints with separate access considerations. Logout and session inspection require authentication. Phase 1 beneficiaries submit their own requests; third-party requester access is deferred. The legacy `Requester` role grants no Phase 1 permissions. Coordinator operations allow both Coordinator and Administrator, while record access also checks beneficiary ownership, active representative membership or referral assignment as applicable. P1-10 owns this authorization boundary; P1-16 retains charity decision workflow and eligibility behavior. The `Beneficiary` role is seeded role data, not a new table or migration. Never return password hashes, storage keys, internal authorization details or sensitive records in logs. Use least-privilege projections for third-party requesters. Cookie authentication requires HTTPS, CSRF protection, secure cross-origin configuration if deployment changes, and no sensitive browser caching. Email verification, identity verification and operational support procedures are not included in this signup increment and require validation before real use.

### Current session and antiforgery contract

`GET /api/v1/auth/antiforgery` is anonymous and returns a request token and the header name `X-CSRF-TOKEN`; retain its antiforgery cookie and send both cookie and token on unsafe `/api/v1` requests, including registration and login. Obtain a fresh token after authentication changes. Missing or invalid tokens return 400 Problem Details. Authentication and authorization challenges return HTTP 401 and 403 without browser redirects; their responses currently have no promised Problem Details body.

The Identity authentication cookie and antiforgery cookie are configured as `Secure`, `HttpOnly` and `SameSite=Strict`. Authentication tickets expire after eight hours without sliding renewal. Cookies require HTTPS. The local setup is for fictional data; production key persistence and deployment policies are separate work. P1-10's current candidate verifies login/logout and applies the role policy above; the local full software suite passed 69/69 on 13 November against isolated PostgreSQL and private S3-compatible storage. The candidate remains unmerged until its PR checks and post-merge workflow pass.

## Integrity, evidence and verification

Use a reviewed PostgreSQL transaction and locking protocol for every balance-affecting writer. The [database design](database-design.md#allocation-and-concurrency-invariant) proposes hierarchy and request locks; P1-53 must extend and validate a consistent order for all affected capacity rows before implementation is claimed safe. Within the transaction recalculate current quantities and recipient eligibility, enforce assigned and released bounds, append history, then commit atomically. Use application-managed UUID concurrency tokens for stale edits. Retry deadlocks only with safe idempotency; never perform file transfer within the database transaction.

Store evidence outside the web root with opaque keys, staged uploads and private authorized download endpoints. Validate allowed file types and size, and plan malware scanning, encryption, retention and orphan cleanup before real use. File-store and database operations are not atomic: finalize only after metadata is committed and reconcile failed stages; backup and restore both stores together.

Implement integration tests against isolated PostgreSQL, not an in-memory substitute: initial and upgrade migrations; UUID and reference uniqueness during concurrent creation; unauthorized role, membership and unrelated-record access including exact-reference and evidence lookup; charity and contributor eligibility; concurrent competing allocations and accept/release operations; the SRS ten-box partial-fulfillment example; split-parent and cycle rules; failed upload cleanup and database/file restore. Exercise correct status codes and stale updates. Use fictional data and evidence. Test the proposed post-acceptance dispute freeze, correction and ancestor propagation separately if that increment is validated.

## Phase 1 catalog, capacity and reminders

These are planned capabilities; exact route shapes and schemas require feature design rather than an inferred contract. A coordinator manages versioned service categories and unit standards with structured component names, quantities and units (P1-12–P1-15, P1-51). New requests use current versions; historical needs, capacity and referrals retain their versions. The interim P1-33 decision allows only an exact-version match for outstanding needs until reviewed; incompatible substitution is prohibited and an unmatched need stays open.

An approved charity selects services and records nonnegative **available-from-now** capacity in platform-standard units (P1-18–P1-23). An update replaces the available balance without rewriting prior commitments; subsequent assignments deduct capacity. At the Africa/Cairo calendar-day boundary, a service/version without a current update is frozen for new referrals, independently of other services. A current zero is distinct from a stale value. Eligible matching and split assignments must respect charity approval, service and compatible standard versions, freshness, available capacity and remaining need (P1-32–P1-35, P1-53).

For each charity with one or more stale services, the planned 08:00 Cairo job records one daily reminder intent and send attempts using the local email catcher (P1-24–P1-26, P1-52). Retry and ambiguous SMTP outcomes must remain observable; SMTP acceptance does not prove mailbox delivery or exactly-once external delivery. The web dashboard exposes the daily capacity task. No real participant, delivery or transfer is implied by the fictional-data demo.

## Phase sequencing and acceptance

Phase 1 demonstrates beneficiary and charity accounts, coordinator charity approval and standards, daily capacity and reminders, self-only multi-need intake, coordinator review and matching, partial and split referrals, private evidence, authorized history and explicit closure. Future work includes contributor approval, third-party intake, email verification, inventory-to-capacity calculations, and proposed late-dispute/correction workflows. An accepted outcome is a coordinator-reviewed report, not independent proof of delivery.

Future acceptance checks include: unauthorized and unrelated access denial; coordinator-only review; zero versus stale capacity at Cairo midnight; one reminder intent across several stale services, retries and ambiguous sends; compatible version matching; competing capacity updates and assignments on isolated PostgreSQL; no double counting across split needs and accepted reports; and refusal to close before all needs are fulfilled and accepted. These are planned tests, not results.
