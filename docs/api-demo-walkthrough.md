# API demo walkthrough

**Current status (21 November 2026):** the API exposes the outcome report and private evidence routes described below. PR #118 added acceptance-focused coverage for an unassigned representative, unsupported media/signatures and oversized evidence; the API CI passed its isolated PostgreSQL/S3 verification. This procedure is not evidence that every workflow has been verified. The implementation baseline is recorded in the [SRS capability assessment](SRS.md#appendix-phase-1-implementation-baseline-and-verification).

This walkthrough is for fictional data only. Start PostgreSQL, S3 storage and the API using the [README](../README.md), apply migrations, and explicitly seed development accounts. Use an HTTPS-capable API client that keeps separate cookie jars for each fictional actor. The OpenAPI document is available at `/openapi/v1.json` in Development. Responses and exact field names should be checked there before running this walkthrough.

For every actor session, first call `GET /api/v1/auth/antiforgery`; send the returned `requestToken` in the `X-CSRF-TOKEN` header on every POST or PUT, including registration, login and file uploads. The client must preserve the accompanying antiforgery cookie. Obtain a new token after login or logout. The API's secure cookies require HTTPS. Registration creates an account but does not sign the participant in; call login separately.

### Current P1-09 signup routes

These routes replace the former shared `/auth/register` endpoint:

- `POST /api/v1/auth/register/beneficiary` accepts `displayName`, `email`, `password`, optional `contactDetails`, and `isFamily`. It creates a UUID account with the `Beneficiary` role and a linked beneficiary profile; the response returns both IDs and the profile's `BEN` reference. Login remains a separate request.
- `POST /api/v1/auth/register/charity` accepts `representativeDisplayName`, `email`, `password`, `organizationName`, `contactDetails`, and optional `registrationInformation`. It creates a UUID account, representative membership, and pending inactive charity application; the response returns the account and application IDs and the `REC` reference. Login remains separate. Coordinator decisions are handled by P1-16.

Both routes are anonymous signup operations protected by the P1-08 antiforgery contract. Email uniqueness is global across account types. A pending charity cannot receive referrals. Registration does not include email verification or third-party requester signup.

### Current API demo procedure

1. **Charity representative:** `POST /api/v1/auth/register/charity` with fictional `representativeDisplayName`, `email`, `password`, `organizationName`, `contactDetails`, and optional `registrationInformation`. The response returns `accountId`, `recipientId` and `reference`; the application is pending and inactive. Call `POST /api/v1/auth/login` separately, then retrieve `GET /api/v1/recipients/{recipientId}` for its current `version`. If supporting information is required, upload a fictional PDF, JPEG or PNG through `/recipients/{id}/attachments`.
2. **Coordinator or Administrator:** log in in a separate session. Administrator inherits Coordinator permissions. Retrieve the application through `GET /api/v1/recipients/{id}` and submit `POST /api/v1/recipients/{id}/decisions` with `decision: "Approved"`, the current `version` and an optional reason. The access boundary is covered by P1-10; P1-16 retains the full decision and eligibility acceptance.
3. **Beneficiary:** `POST /api/v1/auth/register/beneficiary` with fictional `displayName`, `email`, `password`, optional `contactDetails` and `isFamily`. The response returns `beneficiaryId` and a `BEN` reference. Call login separately, then submit `POST /api/v1/requests` using that `beneficiaryId`, a `description`, and both `authorityConfirmed` and `sharingAgreed` set to true. Record the request `id` and `version`.
4. **Coordinator or Administrator:** review using `POST /api/v1/requests/{id}/decisions` with `decision: "Accepted"`, `category: "Goods"`, `requiredQuantity: 1`, `unit: "box"`, and the request `version`. Create the referral through `POST /api/v1/requests/{id}/referrals`, with the approved `recipientId`, `assignedQuantity: 1`, a `scopeDescription`, and the updated request `version`. Record the referral `id`.
5. **Charity representative:** `POST /api/v1/referrals/{id}/outcomes` with `reportedQuantity: 1` and a fictional `description` addressing delivery and receipt. Upload a fictional PDF, JPEG or PNG (up to 10 MiB) as the single multipart file to `POST /api/v1/outcomes/{id}/attachments`. Check that `GET /api/v1/attachments/{attachmentId}/content` returns the file only to an authorized actor. Submit with `POST /api/v1/outcomes/{id}/submit` and its `version`.
6. **Coordinator or Administrator:** review through `POST /api/v1/outcomes/{id}/reviews` with `decision: "Accepted"`, the submitted outcome's `version`, and optional reason. Inspect `GET /api/v1/requests/{id}/progress` and the request/referral history routes using permitted sessions. Beneficiaries see their own needs and assigned portions; each representative sees only needs with a visible assignment and that representative's referral/outcome details. Representatives receive null request status/description and null need status, required quantity and remaining quantity so aggregates across other charities are not exposed. Coordinators see all relevant decisions. A coordinator's acceptance is a review, not independent proof.

Per-need progress includes referrals created after the referral-to-need association is deployed. Existing referrals remain unlinked because their historical need cannot be inferred safely; those referral quantities are not included in per-need totals until reconciled.

Also try a request without authority confirmation, a pending charity referral, an unrelated actor reading the request or attachment, and outcome submission without evidence. These should be rejected. Exact-reference lookup is available on the list endpoints, subject to authorization. This document is a procedure, not evidence that every scenario has been verified. Do not use real personal information or evidence while the demo and storage recovery processes remain under development.
