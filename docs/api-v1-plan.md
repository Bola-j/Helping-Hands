# API v1 implementation plan

Status: **plan, not implemented**. The running application currently exposes only `/health`. The confirmed database structure is described in [database design](database-design.md); mappings, endpoints and policies below are implementation decisions to verify through development. The first version includes all BRD first-version features, with a charity-to-referral demonstration first. Late-dispute extensions remain proposed and require validation.

## Platform and delivery

Use .NET 10 minimal APIs with feature route groups, thin handlers, separate request/response DTOs, EF Core and the Npgsql provider. Publish OpenAPI for `/api/v1`; retain `/health` as liveness and add a separate dependency readiness endpoint when PostgreSQL exists. Keep one deployable API and an eventual React Native Web SPA. Use supported compatible .NET 10, EF Core and Npgsql releases, verifying package compatibility before implementation. No business implementation exists yet.

For local development, install the .NET 10 SDK, Docker and a matching `dotnet-ef` tool; start a password-protected isolated PostgreSQL container with a persistent volume and supply `ConnectionStrings__HelpingHands` as an environment variable, locally using the ignored root `.env` and launcher described in the [README](../README.md). Production secrets belong in the deployment environment or a secret manager. Once the data project and packages exist, run `dotnet ef migrations add <Name> --project <data-project> --startup-project src/HelpingHands.Api` and `dotnet ef database update --project <data-project> --startup-project src/HelpingHands.Api` from the repository root. Replace `<data-project>` with the actual project chosen during implementation. Review generated migration and SQL before applying; commit migration and snapshot with the model change. Use a fresh database for initial-migration testing and an existing previous-version database for upgrade testing. Shared deployments run reviewed migration SQL as a controlled step after backup, with a tested restore and forward-fix plan; do not auto-migrate on app startup. Never commit credentials.

## IDs and references

Each table, including role, join and history tables, has a UUID primary key generated by the server; foreign keys use UUID. Join tables retain unique constraints on their original key pairs; subtype tables retain the recipient UUID as both PK and FK. UUIDs are the stable route and relationship identifiers, never authorization credentials.

Persist a separate immutable reference for beneficiary (`BEN`), recipient application/profile (`REC`), request (`REQ`), referral (`REF`) and outcome (`OUT`). The application and its resulting recipient profile share the same recipient record and reference. Format is `PREFIX-` followed by a zero-padded decimal sequence of at least eight digits, for example `REQ-00000001`; numbers may grow beyond eight digits up to the PostgreSQL sequence limit and are never recycled. Maintain one PostgreSQL sequence per prefix, allocate with `nextval` on the server at creation, and enforce a unique reference index on each table. Sequence gaps after rollback or failed requests are expected; they convey no counts, ordering guarantees across transaction commits, or secrecy. Do not accept client-supplied references or derive them by truncating UUIDs. Return `id` and `reference` in resource DTOs. Support exact `reference` filtering on authorized list endpoints; enforce the same involvement checks as UUID lookup and do not disclose whether an inaccessible reference exists. Future user-facing records needing references require a reviewed migration and prefix.

## API contracts and authorization

Routes below are planned under `/api/v1`; `{id}` is a UUID. Use JSON DTOs, UTC timestamps and decimal quantities; uploads use multipart form data. Return `201` with `Location` for creation, `204` for successful commands without a response, and stable RFC 9457 Problem Details for errors: `400` invalid input, `401` unauthenticated, `403` denied where disclosure is safe, `404` missing or concealed resource, and `409` invalid transition, stale version or allocation conflict. Lists use bounded page size (default 25, maximum 100), stable ordering and opaque cursor; search and pagination apply after authorization. Include a concurrency version in mutable resource responses and require it for updates, returning `409` when stale. Define DTO fields and detailed transitions against the SRS before coding each feature.

| Feature | Planned routes | Access and behavior |
| --- | --- | --- |
| Identity | `GET /auth/antiforgery`, `/auth/me`; `POST /auth/register`, `/auth/login`, `/auth/logout` | ASP.NET Core Identity with secure HttpOnly, Secure, SameSite authentication cookies; same-origin SPA/API behind a reverse proxy; antiforgery protection on unsafe browser requests, login throttling and secure account recovery. Protect credentials with Identity; provision initial administrators through a controlled deployment process. |
| Recipient applications | `POST /recipients`; `GET /recipients`, `GET /recipients/{id}`; `POST /recipients/{id}/attachments`; `POST /recipients/{id}/decisions` | Authenticated applicant manages own application; administrator reviews charity, coordinator reviews contributor. Only approved active recipients can receive referrals. Membership and actor checks apply to each operation. |
| Beneficiaries and intake | `POST /beneficiaries`, `GET /beneficiaries`, `GET /beneficiaries/{id}`; `POST /requests`, `GET /requests`, `GET /requests/{id}` | Authenticated requester or coordinator submits with authority and sharing confirmation; third-party requesters see only permitted information. List supports exact reference filter. |
| Review and split | `POST /requests/{id}/decisions`, `/requests/{id}/splits` | Coordinator classifies, requests clarification, accepts or rejects with reason; split children retain links and split parents cannot be allocated. |
| Referral | `POST /requests/{id}/referrals`; `GET /referrals`, `GET /referrals/{id}`; `POST /referrals/{id}/releases` | Coordinator assigns available portions to eligible recipients and explicitly releases undelivered portions. Assigned recipient representatives view only their referrals. |
| Outcome and evidence | `POST /referrals/{id}/outcomes`; `GET /outcomes`, `GET /outcomes/{id}`; `POST /outcomes/{id}/attachments`, `/outcomes/{id}/submit`, `/outcomes/{id}/reviews`; `GET /attachments/{id}/content` | Involved representatives draft and submit with evidence; coordinator reviews. Every file upload and download checks role and involvement. Acceptance records review, not independent proof. |
| Progress and follow-up | `GET /requests/{id}/history`, `GET /referrals/{id}/history`; `POST /requests/{id}/follow-ups`, `/requests/{id}/closure`; `POST /referrals/{id}/confirmations` | Return only authorized history and progress. Complete only when all required need is accepted; closure with unmet need requires a reason. Confirmations and disagreements are separate from review. |

All endpoints require authentication except registration and login; route handlers and service-layer queries must enforce both role and involvement, including attachment and reference lookup. Roles can overlap. Never return password hashes, storage keys, internal authorization details or sensitive records in logs. Use least-privilege projections for third-party requesters. Cookie authentication requires HTTPS, CSRF protection, secure cross-origin configuration if deployment changes, and no sensitive browser caching. Identity lifecycle, contact verification and operational support procedures require validation before real use.

## Integrity, evidence and verification

Use the [database design's](database-design.md#allocation-and-concurrency-invariant) transaction-scoped shared/exclusive advisory hierarchy lock and ordered request row locks for every balance-affecting writer. Within the transaction recalculate current quantities and recipient eligibility, enforce assigned and released bounds, append history, then commit atomically. Use application-managed UUID concurrency tokens for stale edits. Retry deadlocks only with safe idempotency; never perform file transfer within the database transaction.

Store evidence outside the web root with opaque keys, staged uploads and private authorized download endpoints. Validate allowed file types and size, and plan malware scanning, encryption, retention and orphan cleanup before real use. File-store and database operations are not atomic: finalize only after metadata is committed and reconcile failed stages; backup and restore both stores together.

Implement integration tests against isolated PostgreSQL, not an in-memory substitute: initial and upgrade migrations; UUID and reference uniqueness during concurrent creation; unauthorized role, membership and unrelated-record access including exact-reference and evidence lookup; charity and contributor eligibility; concurrent competing allocations and accept/release operations; the SRS ten-box partial-fulfillment example; split-parent and cycle rules; failed upload cleanup and database/file restore. Exercise correct status codes and stale updates. Use fictional data and evidence. Test the proposed post-acceptance dispute freeze, correction and ancestor propagation separately if that increment is validated.

Core demonstration: charity approval → intake → review → referral → evidence → coordinator review with access controls and history. Subsequent first-version increments add contributors, partial fulfillment and splitting. Optional confirmation and later dispute handling do not turn evidence into independent proof.
