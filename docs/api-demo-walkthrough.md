### Current P1-09 signup routes

These routes replace the former shared `/auth/register` endpoint:

- `POST /api/v1/auth/register/beneficiary` accepts `displayName`, `email`, `password`, optional `contactDetails`, and `isFamily`. It creates a UUID account with the `Beneficiary` role and a linked beneficiary profile; the response returns both IDs and the profile's `BEN` reference. Login remains a separate request.
- `POST /api/v1/auth/register/charity` accepts `representativeDisplayName`, `email`, `password`, `organizationName`, `contactDetails`, and optional `registrationInformation`. It creates a UUID account, representative membership, and pending inactive charity application; the response returns the account and application IDs and the `REC` reference. Login remains separate. Coordinator decisions are handled by P1-16.

Both routes are anonymous signup operations protected by the P1-08 antiforgery contract. Email uniqueness is global across account types. A pending charity cannot receive referrals. Registration does not include email verification or third-party requester signup.

### Current API demo procedure

1. **Charity representative:** `POST /api/v1/auth/register/charity` with fictional `representativeDisplayName`, `email`, `password`, `organizationName`, `contactDetails`, and optional `registrationInformation`. The response returns `accountId`, `recipientId` and `reference`; the application is pending and inactive. Call `POST /api/v1/auth/login` separately, then retrieve `GET /api/v1/recipients/{recipientId}` for its current `version`. If supporting information is required, upload a fictional PDF, JPEG or PNG through `/recipients/{id}/attachments`.
2. **Coordinator or Administrator:** log in in a separate session. Administrator inherits Coordinator permissions. Retrieve the application through `GET /api/v1/recipients/{id}` and submit `POST /api/v1/recipients/{id}/decisions` with `decision: "Approved"`, the current `version` and an optional reason. The access boundary is covered by P1-10; P1-16 retains the full decision and eligibility acceptance.
3. **Beneficiary:** register with `POST /api/v1/auth/register/beneficiary` using fictional `displayName`, `email`, `password`, optional `contactDetails` and `isFamily`. Save `beneficiaryId` from the response, then log in separately. Submit `POST /api/v1/requests/single-need` with `beneficiaryId`, `description`, `authorityConfirmed: true` and `sharingAgreed: true`. Record the returned request `id` and `version`. This focused route creates a legacy-style request for the demo; multi-need `POST /api/v1/requests` remains unchanged.
4. **Coordinator or Administrator:** retrieve the request and submit `POST /api/v1/requests/{id}/decisions` with `decision: "Accepted"`, `category: "Goods"`, `requiredQuantity: 1`, `unit: "box"` and the current `version`. Map an eligible versioned standard through `POST /api/v1/requests/{id}/legacy-standard`, then create a referral through `POST /api/v1/requests/{id}/referrals` using an approved active charity, current service/standard versions and current Cairo-day capacity.
5. **Charity representative:** create or update the referral outcome, upload fictional PDF/JPEG/PNG evidence, and submit the outcome. The charity must own the referral and an attachment is required before submission.
6. **Coordinator or Administrator:** review the submitted outcome through `POST /api/v1/outcomes/{id}/reviews`. Check request and referral history. Verify that an unrelated authenticated account receives `404 Not Found` for the evidence-content route. Coordinator acceptance is a review, not independent proof of delivery.
